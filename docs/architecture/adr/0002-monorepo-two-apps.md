# ADR 0002 — Two independent npm apps, no root workspace

- **Status:** Accepted
- **Date:** 2026-10-22
- **Deciders:** Nghĩa, H.Tài
- **Related:** [ADR 0001](0001-record-architecture-decisions.md), [Project Structure](../../project-structure.md), [Setup](../../setup.md), [Configuration](../../config.md)

## Context

BrewLite has two applications with different runtimes and different dependency trees:

- `apps/api` — NestJS 12, TypeScript, Prisma, Vitest, Node.js server.
- `apps/web` — Next.js 16 App Router, React, TailwindCSS, browser + Node.js SSR.

Both must live in one repository because they are one deliverable: the assignment's Definition of Done (PDF §10) and handover (PDF §11) treat the repo as the product, and the end-to-end flow spans both apps (PDF §5). A single repo also matches how the team works — one branch, one PR, one review, one evidence note per task (`working-agreement.md` §4).

The scaffold was generated by Nest CLI into `apps/api` and `create-next-app` into `apps/web`. Both commands produced their own `package.json`, `package-lock.json`, and config files. The repository root currently has **no** `package.json` and no workspace configuration.

The decision to make is how the two apps share the repo:

1. **Independent apps, per-app npm install** (current state).
2. **npm workspaces** with a root `package.json` and hoisted dependencies.
3. **A monorepo tool** (Turborepo, Nx, pnpm workspaces) on top of either.

The choice affects: how dependencies are installed and locked, how CI runs, how scripts are invoked, how Docker builds resolve dependencies, and how much tooling the team must learn. It also affects a subtle correctness property: the two apps must be able to disagree on versions of shared transitive dependencies (e.g. different `typescript` majors) without one silently winning.

Constraints:

- Team of 5 students, one semester, limited time for tooling setup.
- Graded on process and deliverable, not on monorepo tooling sophistication.
- Docker Compose (Phase 2+, Task 57.0/9) must be able to build each app independently.
- Each app's test runner and build must remain debuggable by a teammate who has never used a monorepo tool.

## Decision

BrewLite uses **two independent npm applications in one repository, with no root `package.json` and no npm workspaces.**

Rules that follow from this:

1. **No root `package.json`.** The repository root contains no dependency manifest. `npm install` at the root is invalid; it either fails or creates a stray lockfile that must not be committed.
2. **Per-app install and lockfile.** Dependencies are installed from `apps/api` and `apps/web` separately. Each app owns its `package.json` and `package-lock.json`. A dependency change is committed with the lockfile of the app that owns it.
3. **Per-app scripts.** `npm run <script>` runs from the owning app's directory. There is no root script that fans out to both apps. If a cross-app task is needed (e.g. "run both in dev"), it is documented as two terminal commands in `docs/setup.md` §7, not as a root script.
4. **No shared package in Phase 1.** Code shared between apps (e.g. types, the pricing rule) is duplicated with an explicit sync mechanism (the pricing fixture in `ui-decisions.md` §4.2), not extracted into a `packages/shared` workspace. If sharing grows beyond one file, the team reopens this ADR.
5. **Path references are relative and explicit.** Docs, scripts, and Dockerfiles refer to `apps/api/...` and `apps/web/...`; they do not assume a hoisted `node_modules` at the root.
6. **CI (Phase 2+) runs per app.** A workflow may use a matrix or two jobs, but each job installs and builds inside one app directory. It does not run a root install.

The layout is documented in `project-structure.md` §"Current generated structure" and §"Node.js packages and commands"; this ADR records the *decision* behind it.

## Consequences

### Positive

- **Zero setup cost.** The scaffold is already in this shape. No migration, no root manifest, no tooling to learn.
- **Dependency isolation is real.** `apps/api` and `apps/web` can use different major versions of the same transitive dependency without hoisting arbitration. This is the property that monorepo tools work hardest to give you; here it is the default.
- **Each app is debuggable in isolation.** A teammate can `cd apps/api && npm install && npm test` and understand everything that happened. There is no hidden root-level resolution step.
- **Docker builds are independent.** `apps/api/Dockerfile` and `apps/web/Dockerfile` can each `COPY` their own `package.json` and `package-lock.json`; there is no root context to reason about. This matters for Task 57.0/9 (docker-compose).
- **Lockfile diffs are per-app.** A PR that bumps an API dependency touches only `apps/api/package-lock.json`; the web lockfile is untouched. Reviewers see exactly what changed.
- **Matches the assignment's expectations.** The PDF does not ask for a monorepo tool; adding one is unrequested complexity that competes with graded work.

### Negative / costs

- **Duplicate installs.** `node_modules` exists twice. Disk and install time are roughly the sum of the two apps. This is acceptable on a student laptop and in CI (two jobs, each cached independently).
- **No cross-app script.** "Run both in dev" is two terminal commands, documented rather than scripted. If a teammate forgets the second terminal, they notice quickly (the web app can't reach the API).
- **No shared package.** Types and the pricing rule are duplicated with a fixture. This is a deliberate trade-off (see Alternatives); the fixture is the sync mechanism, and a PR that changes one side without the other fails review (`ui-decisions.md` §4.2).
- **Version drift risk.** Because dependencies are not hoisted, the two apps can drift on shared libraries (e.g. `typescript`). Mitigation: a Phase 2+ CI check that compares `typescript`, `eslint`, and `vitest` versions across apps and warns on mismatch. Not a Phase 1 requirement.
- **No workspace-level tooling.** Commands like "test all" or "lint all" do not exist at the root. If the team later wants them, that is the trigger to reopen this ADR (see "When to revisit").

### Neutral

- This decision does not prevent adding a monorepo tool later; it only says the team is not adding one now. The migration path (npm workspaces, then Turborepo if needed) is well-trodden.
- It does not affect the *directory* layout. `apps/api` and `apps/web` would be the same directories under a workspace; only the root manifest and resolution would change.

## Alternatives considered

| Alternative                                                      | Why rejected                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **npm workspaces** (root `package.json`, hoisted `node_modules`) | Hoisting can silently resolve a transitive dependency to one app's version, which is exactly the isolation this project benefits from. It also adds a root manifest that `setup.md` and `project-structure.md` would have to explain, and a `workspaces` migration for two apps that don't share code is net-negative. Revisit only if a `packages/shared` workspace is needed. |
| **Turborepo / Nx**                                               | Adds a build system, task graph, and caching layer that the team would have to learn and maintain. The benefit (faster CI, cross-app task orchestration) is real for large monorepos and not real for two apps built by five students. Unrequested complexity.                                                                                                                  |
| **pnpm workspaces**                                              | Same hoisting/root-manifest concerns as npm workspaces, plus a package-manager change the scaffold does not use. The scaffold's `package-lock.json` files are npm's; switching to pnpm means regenerating both and updating `setup.md`. Not justified by any Phase 1 requirement.                                                                                               |
| **Two separate repositories**                                    | The deliverable is one repo (PDF §11). Two repos double the branch/PR/review overhead and make the end-to-end flow (web → API) harder to review as one change. Rejected on process grounds, not technical.                                                                                                                                                                      |
| **A `packages/shared` workspace for types and pricing**          | Tempting, but it forces a workspace tool and a build step for one file. The pricing fixture (`ui-decisions.md` §4.2) solves the same sync problem with a test instead of a package. If a second shared concern appears (e.g. a shared DTO library for API contract), reopen this ADR.                                                                                           |
| **Root `package.json` with `concurrently` to run both apps**     | This is a thin convenience that creates the illusion of a workspace without the isolation. It also puts a dependency at the root, which rule 1 forbids. The two-terminal approach in `setup.md` §7 is simpler and more transparent.                                                                                                                                             |

## When to revisit

Reopen this ADR (new ADR superseding 0002) if any of the following becomes true:

- A second piece of code must be shared between apps beyond the pricing rule (e.g. a shared DTO/type library for the API contract).
- CI build time becomes dominated by duplicate installs, and caching two independent jobs is not enough.
- The team grows beyond the current 5 and cross-app task orchestration becomes a real coordination cost.
- Docker Compose (Task 57.0/9) reveals that independent builds are harder to wire than a workspace would be. (Unlikely — independent builds are usually easier.)

Until then, the current layout stands.

## Notes on choices I made (so you can accept or override)

1. **This ADR is mostly "no" decisions, and that's the point.** The team didn't choose a monorepo tool; it chose *not* to. An ADR that only records what you did is half an ADR — the value is in recording what you rejected and why, so the next person doesn't re-propose npm workspaces in Week 6. The Alternatives table is the longest section because that's where the real reasoning lives.

2. **I made dependency isolation a *positive consequence*, not just a neutral fact.** The most common argument *for* workspaces is "shared dependencies," and the most common argument *against* them is "hoisting surprises." For two apps that don't share code, isolation is the feature, not the cost. Saying so explicitly means a future "should we add workspaces?" conversation starts from the right premise.

3. **The "When to revisit" section is what keeps this ADR from becoming dogma.** An `Accepted` ADR that says "never reconsider" is worse than no ADR — it turns a time-bound decision into a rule. Listing the specific conditions (shared code beyond pricing, CI time, team growth, Docker wiring) means the next person can check "has this happened yet?" instead of re-arguing from scratch. This mirrors `config.md` §7's open-items pattern: decisions have owners and closing conditions.

4. **The pricing fixture is named three times** (rule 4, Negative/costs, Alternatives). That's deliberate: it's the one place where "no shared package" has a real cost, and the fixture is the thing that pays it. If someone later argues for a `packages/shared` workspace, the first question is "does the fixture still suffice?" — and this ADR has the answer in three places.

5. **The open-questions table is small, and two of its three rows point at things that already exist.** That's intentional: an ADR that closes a decision should have few open questions, and the ones it has should be verification tasks ("confirm no root `package.json` at handover"), not unresolved design questions. Compare ADR 0001, which has three genuinely open questions because the meta-decision is still settling. If an ADR's open-questions table grows, it's a signal the decision isn't actually `Accepted` yet.

6. **One forward reference to honor:** the "CI version-drift check" in the open-questions table is a Phase 2+ item. It's named here so that when the first CI workflow lands, someone remembers to check it — but it's explicitly *not* a Phase 1 requirement. Don't let it creep into Phase 1 scope; the ADR says "not a Phase 1 requirement" in the Negative/costs section too, twice for safety.

7. **A small thing to verify:** `project-structure.md` says "The root currently has no npm workspace package." This ADR says the same thing in rule 1. If a teammate has already created a root `package.json` (e.g. to run `concurrently`), this ADR is now describing something that doesn't exist. The first open question is the check for exactly that — worth doing at the next standup, before Task 6.0's evidence note is re-verified.
